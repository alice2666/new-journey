### 问题 2 —— `all-picture` 出现时整体放大再缩回原尺寸（提交 `83c8c48`）

**实现**：`@keyframes picPop { 0%,40% scale(1) → 70% scale(1.08) → 100% scale(1) }`，`1s ease-in-out`；
`#all-picture.pop` + **`.pop.glow` 组合规则**；`runAct6Finish()` 里在 `classList.add('in')` 的**同一帧**再加 `.pop`。

**★ 三个实现要点（都写进了 CSS 注释，都是「看起来能跑、其实静默出错」的坑）**

1. **`.pop.glow` 的组合规则是必需的，不是可选优化**：`.pop` 与 `.glow` **同帧**挂上（差一个微任务），
   而 CSS 的 `animation` 是**整体替换、不叠加** —— 两条**同特异性**规则按「后定义者胜」会
   **静默吃掉一个动画**（症状：「要么不弹、要么发光没了」，**且不报任何错**）。→ **本地新坑，已写入 MEMORY。**
2. **「等淡入走完再弹」用 keyframes 的前 40% 原地不动表达**，**不用 `animation-delay` + `fill-mode`** ——
   后者会让 `transform` 被动画的填充值**长期接管**，留下一层隐性状态。
3. **`.pop` 只加不摘**：动画 `1` 次迭代、无 fill-mode，播完 `transform` **自然回落**；
   若用 `animationend` 摘类，会让**同帧并存的 `picGlow` 被重启**（相位从 59% 跳回 0%）→ **一次肉眼可见的亮度闪**。
   这是「**一个动画结束**」与「**另一个动画被重启**」的耦合陷阱。

**★ 测试（`a6c` 51 → 65，14 项）**：在页面内装 `__pop` 探针，**采样动画期的 `computed transform`**
（布局坐标在这件事上恒为常数，什么也测不出来），并同时采 `matrix` 的 4 个分量以区分「等比整体缩放」与「拉扁 / 旋转」。
实测：**峰值 `1.0800`** / **末次 `1.0000`** / **首次放大在 930ms**（先淡入后弹的顺序成立）/ `skewMax = 0` /
`|scaleX−scaleY| = 0` / `transform-origin = 320px 258.5px` / **动画期布局坐标越界 0 次** / 结束后 `transform = none`。

**★ 两条首版假红（都已修正并写入文档 §13.17）**
1. 并存后 `animationName` 是**逗号列表** `'picPop, picGlow'` → 旧断言 `=== 'picGlow'` **假红**；
   同理 `animationDuration` / `IterationCount`（`'1s, 1.6s'` / `'1, infinite'`）→ 改为**按名字取索引**再比。
2. 断言「**无残留形变**」时，`__pop.done` 的判据是「已放大过且回到 <1.005」，**它在动画收尾前就会置位**
   （当刻 `transform` 仍是 `matrix(1.0019, …)`）→ 必须**再等一个完整周期**（`sleep(350)`）才量。

**★ 截图干扰**：截图会**卡主线程**，若在 pop 期间截，探针会**错过整个 pop**。故把 `shot('a6c-1-glow')`
**从 pop 之前挪到 pop 之后**；另加一张「定格在峰值」的 `a6c-2-pop-peak.png`（临时钉 `scale(1.08)`、截完还原，
**放在全部断言之后**、不参与任何断言）。目检：古画围绕画心整体放大（左右各溢出约 26px = 640×0.08/2），
**木桌 / 右侧底板 / 两个圆钮位置完全不变**。

**文档**：需求 **v2.22 · Q58**（§9.6 新增子项、§12.4.3 决议）；开发计划 **v2.17**（§6.24 表格 + CSS + 三个实现要点、§10.7 自测项、§11.1 项数、**新增 §13.17**）。

### ★ 本轮最重要的发现：「所有 `opacity` 断言全绿、画面却全黑」

第八幕首版 `runAct8()` **漏了 `blackout.classList.remove('in')`** → E1 起**全黑到片尾**。而 ——
`state().act8.active`、`effOpacity('#act8')` / `('#bg-balck')` / `('#the-end')` **全部返回 1，一条断言都不失败**。
根因：**`effOpacity` 沿祖先链累乘，只回答「这一层有没有被父级压透明」，完全不反映「上面还压着一层不透明黑幕」。**

**发现路径不是测试，是目检**：`a7-2-the-end.png` 截图全黑 → 用 PIL 量化（`maxsum = 0`、`brightPx = 0`）坐实。

**据此补的两道防线（长期资产）**：
1. **独立断言**：对**每一个全屏黑幕 / 蒙层**，单独断「**它自己**的 `opacity === 0`」，而不要只断被它盖住的元素
   （`a7` 里 `#blackout` 的 `opacity === 0` + `pointer-events === none` 两条互相独立的证据）。
2. **新增 `pngStats(file)`**：手工解 PNG（IHDR/IDAT/IEND + 5 种 filter 反算），返回 `{ w, h, maxLuma, bright, corner }`，
   在 `a7` / `full4` 关键帧上断「亮像素数 / 最亮度 / 底色是否 `#101010`」。
   **这是唯一能拦住「断言全绿、画面全黑」的手段。**

→ **MEMORY 级教训：`opacity` 断言只证明「没被父级压透明」，不证明「没被别的东西盖住」。「透明」与「被盖住」是两件事。**
