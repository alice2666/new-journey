**测试脚本踩到的 3 个坑（都是测试自身的问题，不是产品 bug）：**
1. `.in` 类一加上 `pointer-events` 就变 auto，但此时 `busy` 锁未释放、点击监听尚未挂载，**立刻点会被吞掉** → 点击前必须等入场动画结束（600ms）。这个是第一次跑就超时的原因。
2. `getBoundingClientRect()` 会被 `#hand` 的 tap 缩放动画污染导致断言抖动 → 几何断言统一改读**布局坐标**（沿 offsetParent 链累加 offsetLeft/offsetTop）。
3. `computed transform` 是 `matrix(1, 0, 0, 1, 0, 0)`，用 `replace(/[^0-9.]/g,'')` 剥字符会把 scale=1 拼成 `100100` → 必须取 `matrix(` 后第一个参数。

### 第三轮：台词下移 20px + 支持 3 行台词（锚点从 bottom 改为 top）

用户要求：**台词 2-3 行时整体下移 20px；只能在浅蓝底板上、不压其他物件**。
给的两个数字互相矛盾（「下移20px」→ bottom=50，「bottom 70改成65」→ 只下移5px），
追问后用户选定：**底边距画面底 50px（下移 20px）**，且**必须支持 3 行台词**。

- **几何上不可兼得，这是本轮的核心结论**。姓名牌 x351–523 横向正压文字左边界(380)上方，
  文字「墨迹顶边」必须 ≥ 755。若用 `bottom` 锚定，行数一多文字往上长：
  | bottom | 2 行墨迹顶边 | 3 行墨迹顶边 | 3 行是否压牌 |
  |---|---|---|---|
  | 70 | 756.4（净空 1.4） | 719 | 压住 36px |
  | 65 | 761.4（净空 6.4） | 724 | 压住 31px |
  | 50 | 776.4（净空 21.4） | 739 | **压住 16px** |
  | 28 | 793.4 | 761.4 | 净空 6.4 ✅ |
  即 bottom 必须 ≤28 才能让 3 行安全，但那样 2 行就明显偏下。
- **解法：把 `#chat-text` 的锚点从 `bottom` 改成 `top`**。行数增加只向下生长：
  - `top: 370.4px`（弹窗内局部坐标！`#chat` 在画布 top:400，画布 y = 770.4）
  - 2 行：框 y770–846 → 底边距画面底 **50px** ✅（下移 20px）
  - 3 行：框 y770–883 → 底边距 13px，仍在底板内 ✅
  - 2 行与 3 行的**墨迹顶边恒为 y≈776.4**（= 原 756.4 下移 20px），正好就是「2-3 行整体下移 20px」
- **踩坑（坐标系）**：`#chat-text` 是 `#chat` 的子元素，CSS `top` 是**弹窗内局部坐标**，
  直接写 `top:770.4` 实测画布 y=1170（= 400 + 770.4）。必须写 `top:370.4`。
  注意 `left:380` 恰好等于画布 x（因为 #chat 的 left=0），`bottom` 也恰好等于距画面底
  （因为 #chat 底边与画面底齐），所以历史上没暴露这个坑 —— **`top` 是第一个会踩到的属性**。
- p1 用例扩到 **36 项**，新增 3 行台词回归：临时注入 `LINE3`（打字机 rAF 已退出，直接改
  `textContent` 不会被覆盖），断言实际行数 = 3、顶边与 2 行相同、墨迹顶边仍为 776.4、
  底边 ≤ 896，并跑同一套「不压物件」硬约束。

### 第七轮：用户报障「打开后画面不动、第一幕消失」→ 补启动兜底（提交 `ea68e41`）

用户原话：「为什么我打开网页画面动不了，而且之前第一幕开始界面都没有了，整个网页之前的片段呢？」

**排查结论：文件本身没有问题。** 逐一验过：`test.js` 8 用例 241 项全绿；`file://` 直开（**不加任何特殊启动参数**）第一幕正常淡入、START 可点、零控制台报错；26 个资源引用与磁盘路径**逐一大小写匹配**（全部命中，排除「本地 Windows 不区分大小写、换 HTTP 服务就 404」这个经典陷阱）；无 BOM、`charset=UTF-8` 正常；git 工作区干净。**问题出在打开它的环境。**

**但这暴露了本页最脆弱的设计**：所有元素默认 `opacity:0`，全靠脚本加 `.in` 才显示 —— 也就是「**脚本没跑起来 = 全黑 + 点不动 + 零提示**」，这是最难让使用者自行排查的状态。且原代码 `main().catch` **只 `console.error`**，用户屏幕上什么都看不到。

**四层兜底（已实现）**：

1. `<noscript>`：JS 被禁用时给出说明。
2. **引擎能力自检**：缺 `Promise` / `classList` / `requestAnimationFrame` / `Element.closest` 任一 → 报「浏览器版本过旧」+ 列出缺哪几项，随后 `return` 不再往下执行。
3. **启动看门狗**：`window.__njMarkBooted()` 由第一幕打出；6s 内未标记 → 报「启动超时」+ 当前地址。
4. **错误可见化**：`main().catch` 与启动 `try` 均改为调用 `reportFailure()`，把堆栈写到屏幕上。
   面板同时打印 UA、打开方式（是否 `file://`）、窗口尺寸、DPR、缺失能力，并提示按 F12 看 Console。

**两条有价值的一手事实**：

- 页面脚本**全是 ES5 写法**（无 `let`/`const`、箭头函数、模板字面量、`?.`、`await`）→ **语法层面不存在兼容性风险**，风险只在**运行时能力**。实际依赖 `Promise`、`classList`、`requestAnimationFrame`、`Element.closest` → **最低 Chrome 41+ / Edge 15+ / Firefox 44+**；**IE11 缺 `Promise` 与 `Element.closest`，必然黑屏**。
- 新工具 `.workbuddy/tools/boot-check.js`（3 场景 14 项）：用 `Page.addScriptToEvaluateOnNewDocument` 抹掉 `Promise` **成功复现黑屏**（断言第一幕确实未渲染），证明这条兜底路径真实有效。
